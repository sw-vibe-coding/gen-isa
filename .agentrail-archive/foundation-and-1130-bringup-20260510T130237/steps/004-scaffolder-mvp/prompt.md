Step 4 of saga "foundation-and-1130-bringup".

# Goal

Build a Rust binary in this repo (`gen-isa`) that emits per-ISA crate
quintet **skeletons** -- one quintet per ISA, five crates each:
`sw-{slug}-{isa,target,codegen,asm,emulator}`. No spec parsing yet --
that's step 5 (`scaffolder-codegen`).

# Output the scaffolder must produce

Given an invocation like:

```
gen-isa scaffold --slug ibm1130 --display-name "IBM 1130" \
                 --type-name Ibm1130 --out ~/github/sw-comp-history
```

The scaffolder writes five sibling directories under `--out`:

- `sw-ibm1130-isa/`
- `sw-ibm1130-target/`
- `sw-ibm1130-codegen/`
- `sw-ibm1130-asm/`
- `sw-ibm1130-emulator/`

Each contains:

- `Cargo.toml` -- name, version 0.1.0, edition 2024, MIT license,
  description matched to the role, dependencies on framework crates
  via `path = "../../sw-langtools/<framework-crate>"` (or whatever
  the configured layout is).
- `LICENSE` (MIT, 2026 Michael A Wright; copied from `gen-isa/LICENSE`).
- `COPYRIGHT`.
- `README.md` -- one paragraph describing the crate's role + status
  banner ("0.1.0 skeleton, generated by gen-isa") + sibling-layout note.
- `src/lib.rs` -- `//!`-style module doc + per-role module declarations
  (e.g. `pub mod opcode;` etc) + `todo!()` stubs sufficient to compile.
- One module file per submodule (`opcode.rs`, `register.rs`, `encode.rs`,
  `decode.rs`, `branch.rs` for `-isa`; etc), each empty or with a
  `//!` doc and a single placeholder type.
- `tests/smoke.rs` -- a single trivial test asserting the crate
  compiles.
- `.gitignore` -- `/target`.

For the `-target`, `-codegen`, `-asm`, `-emulator` crates the file set
is similar but with their own per-role module structure. See
`gen-isa/docs/porting-guide.md` Sec 7 for the per-crate file layout.

# Constraints

- **No spec parsing.** Step 4 just emits parameterised templates; the
  generator parses the spec in step 5. Hard-coded module structure per
  crate role; no logic that reads opcodes/registers from a TOML.
- **The generated quintet must compile** when its `--out` location is
  a sibling of `~/github/sw-langtools/`. Verify by:
  1. Running the scaffolder against a temporary directory.
  2. Adjusting the path-deps in the generated Cargo.toml so they
     point at the real `sw-langtools/` checkouts (or use a tempdir
     fixture).
  3. `cargo build` succeeds in each generated crate.
- **No other code in `gen-isa`** beyond the scaffolder binary, its
  modules, and a `Cargo.toml`. Per `decisions.md` Sec 1, this repo
  hosts generators only -- no generated artifacts, no compiler code.
- ASCII-only in everything the scaffolder emits.
- Zero clippy warnings in `gen-isa`'s own code.

# Design suggestions (not requirements)

- Top-level CLI: `clap` derive-style. Subcommand `scaffold`. Required
  flags: `--slug`, `--display-name`, `--type-name`, `--out`. Optional:
  `--framework-path` (default: `../sw-langtools` resolved from `--out`),
  `--dry-run`, `--force` (overwrite existing).
- Internal API: `ScaffoldRequest` struct + `scaffold(req: &ScaffoldRequest, fs: &dyn Filesystem) -> Result<...>`.
  Pass a Filesystem trait so tests can use an in-memory FS without
  touching the real disk.
- Use a tiny templating approach (`format!` or a string-replace map);
  do NOT pull in `tera`, `handlebars`, or similar -- not warranted at
  this stage.
- Keep the binary in `src/bin/scaffold.rs` (or `src/main.rs` if the
  repo only ever has one binary). Library code in `src/lib.rs` so
  tests can import it.

# Tests

- Unit tests for the templating helpers (no I/O).
- One integration test that scaffolds a quintet to a `tempfile::TempDir`,
  then runs `cargo build --offline` in each generated crate against a
  fixture sw-langtools layout. (Or asserts file contents match
  golden snapshots.)
- Smoke test: invoke the binary with `--dry-run` and check stdout
  lists the files it would create.

# Acceptance

- `cd ~/github/sw-vibe-coding/gen-isa && cargo build && cargo test &&
   cargo clippy --all-targets --all-features -- -D warnings &&
   cargo fmt --check` all exit 0.
- Running the scaffolder against a tempdir produces a quintet whose
  generated `cargo build` succeeds (path-deps pointing at the real
  `~/github/sw-langtools/` checkouts is acceptable for this step).
- `gen-isa/.gitignore` excludes `/target`.

# What to do this step

1. Read `docs/decisions.md`, `docs/spec-format.md`, and
   `docs/porting-guide.md` Sec 2-7 for the per-crate file shape.
2. Author `Cargo.toml` (binary `gen-isa` + library), `src/lib.rs`,
   `src/bin/scaffold.rs` (or `src/main.rs`), templating helpers,
   and tests.
3. Verify locally (build + test + clippy + fmt).
4. Run the scaffolder against a tempdir; verify the output compiles.
5. Update `docs/status.md` (Recent changes + crate-state hint).
6. `git add` and commit (a single commit for the scaffolder is fine).
7. `agentrail complete` with:
   - `--summary` describing what got built and acceptance evidence.
   - `--reward 1`.
   - `--actions` describing approach.
   - `--next-slug scaffolder-codegen`
   - `--next-prompt` defining step 5 (extend the scaffolder to parse
     the TOML spec and emit `opcode.rs`, `register.rs`, `encode.rs`,
     `decode.rs`, `branch.rs`, `lib.rs` (`Architecture` impl) from
     the spec; keep the rest of the quintet as templates).
8. STOP.

# What NOT to do

- Don't introduce per-ISA logic in this step (no spec parsing).
- Don't generate code that depends on traits we haven't shipped to
  `sw-langtools` yet.
- Don't pre-write opcode tables or register tables for any ISA --
  those come from the spec, parsed in step 5.
- Don't push generated crates anywhere in this step. The scaffolder's
  job is to write files; pushing is a step-7+ concern.
